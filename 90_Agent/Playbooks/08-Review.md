# Change and delivery review

Apply [Evidence and Clarification Policy](../Evidence-and-Clarification-Policy.md) whenever information is unclear, missing or conflicting. Ask the user for clarification or relevant material; keep dependent conclusions pending and continue only supported independent work. This condition also applies to the completion criteria below.

1. Read Settings and Language Policy, the change and relevant baselines. Compare every changed factual assertion and required behavior with its original evidence, including inherited claims, measurements, absence statements and exception handling. Surface unsupported premises through actual questions. Run impact ID, validate and coverage; sync changed sources as needed. These structural checks do not perform source-to-claim review.
2. Inspect downstream PBIs, tests and releases after requirement, terminology or contract changes. Capturing a candidate creates no approval. When a new draft coexists with an old baseline, state each PBI's execution basis.
3. Record motivation, options, scope/effort/date differences and the decision owner in Change. Update remaining work/allocation and run plan if capacity is affected.
4. For status work, run status then analyze needed dates, overdue items, risks and external waits. Actions need owners and dates. External sending remains within user authorization.
5. Use the [acceptance/release procedure](../../08_Verification/Acceptance-and-Release.md) to review tests, UAT, data, cutover, rollback and operations. Follow the [benefits procedure](../../09_Operations/Benefits-and-Costs.md) for post-release learning.

Complete when exceptions are corrected or assigned, approvals/test outcomes/releases have actual evidence, and simulations remain distinguishable. Mechanical checks do not replace semantic review.
